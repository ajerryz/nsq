# nsqd
nsqd 是 NSQ 集群的 “工作节点”，是消息处理的核心，其核心功能包括消息的接收、存储、投递和确认。

# nsqd简单介绍

1.核心角色与功能
- 接收消息：通过 TCP 或 HTTP 接口接收生产者发送的消息，并根据消息的 “主题（Topic）” 分类。
- 存储消息：消息默认先存于内存（高效），当内存达到阈值（可配置）时，会持久化到磁盘（防止丢失）。
- 投递消息：根据消费者订阅的 “通道（Channel）”，将消息主动推送给消费者（推模式，Push）。
- 消息确认：处理消费者的消息确认（如成功处理的 FIN、需要重试的 REQ），确保消息不丢失或重复投递。

2,关键概念  
sqd 通过 Topic 和 Channel 实现消息的分类与分发，是理解 nsqd 工作机制的核心：
- Topic：消息的 “主题”，由生产者指定（如 “用户注册”“订单支付”），是消息的一级分类。一个 nsqd 可管理多个 Topic，每个 Topic 对应一个消息队列。
- Channel：Topic 的 “子通道”，是消息的二级分类，用于将同一 Topic 的消息分发给不同的消费者组（如 “订单支付” Topic 可创建 “通知用户”“记录日志” 两个 Channel，分别由不同服务消费）。
  - 特性:
    - 一个 Topic 可包含多个 Channel，每个 Channel 会收到该 Topic 的所有消息（类似 “广播”）。
    - 同一 Channel 的多个消费者是 “竞争关系”，每个消息只会被其中一个消费者处理（实现负载均衡）。

3.消息处理流程
1. 生产者发送消息：
   - 生产者通过 TCP（高效，适合高吞吐）或 HTTP（简单，适合少量消息）向 nsqd 发送消息，并指定 Topic（如 “order_pay”）。
2. nsqd 接收与存储：
   - nsqd 接收消息后，将其存入该 Topic 对应的内存队列；若内存不足，异步写入磁盘（文件路径可配置，默认 ./data）。
3. 消费者订阅消息：
   - 消费者启动时，通过 nsqlookupd 发现存储目标 Topic 的 nsqd 节点，然后向 nsqd 发送订阅请求（指定 Topic 和 Channel，如 order_pay + notify_user）。
4. nsqd 投递消息：
   - nsqd 为该 Channel 维护一个消息队列，将 Topic 中的消息复制到 Channel 队列，并主动推送给订阅该 Channel 的消费者（推模式）。
5. 消息确认与重试：
   - 消费者成功处理消息后，向 nsqd 发送 FIN <message_id> 确认，nsqd 从 Channel 队列中删除该消息。
   - 若处理失败，消费者发送 REQ <message_id> <timeout>，nsqd 会在 timeout 后重新将消息放入队列重试。
   - 若消费者长时间未确认（超过配置的超时时间），nsqd 会自动重试消息。

4.持久化与容错
- 持久化：nsqd 可配置消息持久化（通过 --mem-queue-size 控制内存队列上限，超过后写入磁盘）。重启 nsqd 时，会从磁盘恢复未处理的消息。
- 容错性：nsqd 节点是独立的（无状态），可水平扩展（增加节点分担负载）。若某 nsqd 故障，生产者可将消息发送到其他节点（需客户端实现多节点投递），消费者通过 nsqlookupd 发现健康节点。

5.配置与启动

nsqd 可通过命令行参数或配置文件调整行为，关键配置如下：
- `--tcp-address`：TCP 服务地址（默认 0.0.0.0:4150，生产者 / 消费者主要用此端口）。
- `--http-address`：HTTP 服务地址（默认 0.0.0.0:4151，用于管理和简单消息发送）。
- `--data-path`：消息持久化目录（默认 ./data）。
- `--mem-queue-size`：每个 Channel 内存队列的最大消息数（超过后写入磁盘，默认 10000）。
- `--lookupd-tcp-address`：关联的 nsqlookupd 地址（用于注册自身信息）。

# nsqd 与其他组件的协作
- 与 nsqlookupd：nsqd 启动后会定期向 nsqlookupd 发送心跳（注册自身地址和 Topic 信息）；当 nsqlookupd 收到消费者的查询请求时，会返回对应的 nsqd 节点列表。
- 与消费者：消费者通过 TCP 连接 nsqd，发送订阅命令（SUB <topic> <channel>），然后持续接收 nsqd 推送的消息，并回复确认命令（FIN/REQ）。

# nsqd特点
- 轻量易扩展：nsqd 无状态，可快速横向扩展（增加节点），适合大规模集群。
- 实时性高：推模式（Push）确保消息快速投递，延迟低。
- 灵活的消息分发：通过 Topic + Channel 实现 “广播”（多 Channel）和 “负载均衡”（多消费者）。
- 可靠性：消息持久化 + 重试机制，避免丢失（但默认单节点存储，需手动实现多节点冗余）。
